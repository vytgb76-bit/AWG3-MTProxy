# AWG3 MTProxy Gateway Guard

**Управление сетевыми правилами для AmneziaWG 3 и MTProxyL (telemt) на Linux-сервере.**

Проект настраивает доступ к MTProxyL только через туннель AmneziaWG, ограничивает исходящие соединения к российским IP-сетям и автоматически восстанавливает управляемые правила после перезагрузки сервера или перезапуска Docker-контейнера.

> [!IMPORTANT]
> Это **надстройка над уже работающими AmneziaWG 3 и MTProxyL**, а не их установщик. Перед применением к удалённому серверу необходим доступ к консоли VPS у провайдера. Установка изменяет действующие правила межсетевого экрана.

## Возможности

- **Изоляция MTProxyL от публичного интернета.** Входящие TCP-соединения на порт прокси блокируются с внешних интерфейсов по IPv4 и IPv6. Соединения из предназначенного для AWG Docker-контейнера разрешаются адресно.
- **Доступ к прокси через AWG 3.** Внутри AWG-контейнера создаются правила DNAT, MASQUERADE и FORWARD для маршрута от клиентов туннеля к MTProxyL на хосте.
- **Блокировка исходящих новых соединений в российские IP-сети.** Применяются IPv4- и IPv6-наборы `ipset`, сформированные на основе общедоступных данных IPdeny. В существующих соединениях допускается ответный трафик `ESTABLISHED,RELATED`.
- **Ограниченные исключения для удалённых AWG-узлов.** Можно указать публичные IPv4-адреса, для которых предусмотрено исключение из фильтрации пересылаемого UDP-трафика AWG.
- **Автоматическое обнаружение Docker-сети.** При поддерживаемой конфигурации определяется связка сетевых интерфейсов контейнера и хоста; смена имени `eth0`/`eth1` не требует ручного изменения NAT-правил.
- **Восстановление после перезагрузки.** Правила восстанавливаются службами systemd и периодической проверкой состояния моста.
- **Ежедневное обновление адресных списков.** Время задаётся в UTC. При обнаружении пустых или неполных наборов `ipset` используются локально сохранённые списки.
- **Проверка перед применением и откат.** Есть режим `--dry-run`, автоматическая попытка отката при обычной ошибке установки и отдельная команда удаления.
- **Осторожная работа с существующей системой.** Проект не переустанавливает AWG, MTProxyL, Docker, SSH или UFW и не сбрасывает весь межсетевой экран.

## Схема работы

```text
                             Интернет
                                │
              ┌─────────────────┴─────────────────┐
              │                                   │
     UDP-порт AmneziaWG                  TCP-порт MTProxyL
              │                                   │
              ▼                                   ▼
     Контейнер AWG 3                         Блокируется
       интерфейс awg0                     на внешнем INPUT
              │
              │ TCP к внутреннему IP AWG
              │
              ▼
     DNAT внутри контейнера
              │
              ▼
    Docker-мост (контейнер → хост)
              │
              ▼
       MTProxyL / telemt
       TCP-порт на хосте
```

Дополнительно для исходящего трафика хоста и пересылаемого трафика контейнеров действуют цепочки фильтрации:

```text
OUTPUT / FORWARD
       │
       ├── ESTABLISHED,RELATED → пропустить к следующим правилам
       │
       ├── разрешённое исключение AWG UDP → пропустить к следующим правилам
       │
       └── NEW + IP назначения из RU CIDR → REJECT
```

В этой документации используются **только примерные адреса** из частных или зарезервированных для документации диапазонов. Они не являются конфигурацией готового сервера.

## Требования и совместимость

### Предварительно установленные компоненты

1. Linux-сервер с `systemd`, `iptables`/`ip6tables`, `ipset` и Docker.
2. Запущенный контейнер **AmneziaWG 3** с доступным сетевым интерфейсом туннеля (например, `awg0`). Название Docker-контейнера не обязано совпадать с названием протокола.
3. Запущенный **MTProxyL (telemt) непосредственно на хосте**, слушающий выбранный TCP-порт, в том числе loopback.
4. Рабочий SSH-доступ и известный фактический TCP-порт SSH.
5. Доступ по HTTPS к источникам IPv4/IPv6-списков IPdeny во время установки и обновлений.
6. Возможность запуска команд от `root`.

Для поддержки данной схемы AWG-контейнер должен иметь IPv4-адрес на интерфейсе туннеля, включённый `net.ipv4.ip_forward=1`, а также Docker-интерфейс, имеющий сеть, общую с интерфейсом хоста.

### Системные утилиты

Необходимы `python3`, `docker`, `iptables`, `ip6tables`, `iptables-save`, `ip6tables-save`, `ipset`, `ip`, `ss`, `curl`, `nsenter`, `systemctl`, `networkctl` при проверке конфликтов сетевых настроек и `awk`.

На Debian/Ubuntu отсутствующие сетевые утилиты обычно устанавливаются так:

```bash
sudo apt-get update
sudo apt-get install -y iptables ipset curl iproute2 util-linux
```

Python 3, Docker и служба systemd должны быть установлены отдельно. Команда выше **не устанавливает AmneziaWG и MTProxyL**. Совместимость конкретного выпуска ОС, бэкенда `iptables` и правил стороннего файрвола необходимо проверить в тестовом окружении.

> [!WARNING]
> Установка не предназначена для применения поверх предыдущих версий аналогичных правил. Если уже существуют управляемые цепочки, наборы `ipset`, systemd-юниты или метки другого экземпляра, установщик может отказать в запуске во избежание конфликта владения ресурсами.

## Быстрый старт

### 1. Получение исходников

Скопируйте файлы проекта на сервер. Если используется архив, распакуйте его и перейдите в каталог с `install.sh`:

```bash
python3 -m zipfile -e ./eu_awg3_final_v6.zip ./
cd ./eu_awg3_final_v6
```

Если проект получен из Git-репозитория, перейдите в корень репозитория с файлами `install.sh` и `euag3ctl.py`.

### 2. Предварительная проверка

Перед использованием проверьте реальные адреса интерфейсов и слушающие порты:

```bash
docker ps
docker exec amnezia-awg2 ip -br -4 addr
ss -lnt
ip -br -4 addr
ip route show default
```

`amnezia-awg2` здесь — **пример имени контейнера**; замените его, если установлен другой.

Запустите установщик в режиме без изменения правил:

```bash
sudo bash ./install.sh --dry-run \
  --container amnezia-awg2 \
  --awg-interface awg0 \
  --awg-address 10.66.44.1 \
  --awg-cidr 10.66.44.0/24 \
  --mt-port 5443 \
  --tunnel-port 5443 \
  --ssh-port 22 \
  --awg-udp-port 443 \
  --update-at 04:25 \
  --no-fix-ifupdown
```

**Подставьте существующие значения вашей конфигурации.** В частности, адрес `10.66.44.1` должен быть **фактически назначен `awg0`**, иначе проверка завершится ошибкой. Пример предполагает, что Docker-мост определяется автоматически.

`--dry-run` проверяет инструменты, параметры, существование и состояние компонентов, конфликт ресурсов и доступность адресных списков. Он **не создаёт сетевых правил и не записывает рабочую конфигурацию**.

### 3. Установка

Интерактивный запуск:

```bash
sudo bash ./install.sh
```

Для воспроизводимой установки используйте тот же набор явно заданных параметров, что и в `--dry-run`, но без самого флага `--dry-run`:

```bash
sudo bash ./install.sh \
  --container amnezia-awg2 \
  --awg-interface awg0 \
  --awg-address 10.66.44.1 \
  --awg-cidr 10.66.44.0/24 \
  --mt-port 5443 \
  --tunnel-port 5443 \
  --ssh-port 22 \
  --awg-udp-port 443 \
  --update-at 04:25 \
  --no-fix-ifupdown
```

Установка выполняет предварительную проверку, загружает списки CIDR, сохраняет сведения для отката, применяет собственные правила, создаёт службы и таймеры systemd и выполняет локальную проверку TCP-доступа к MTProxyL из сетевого пространства AWG-контейнера.

Установщик не перезагружает сервер автоматически.

### 4. Проверка состояния

```bash
sudo /usr/local/sbin/euag3ctl status
sudo /usr/local/sbin/euag3ctl check
systemctl list-timers --all | grep euag3
systemctl --failed --no-pager
```

Команда `check` проверяет инфраструктурные предпосылки, но не заменяет тест подключения реального AWG-клиента.

## Параметры установки

Все перечисленные параметры передаются после `install.sh`. При отсутствии некоторых аргументов установщик предлагает значения в интерактивном режиме или использует предусмотренные кодом значения. **Для автоматизации задавайте все важные параметры явно.**

| Параметр | Описание | Пример |
|---|---|---|
| `--container` | Имя работающего Docker-контейнера AWG | `amnezia-awg2` |
| `--awg-interface` | Интерфейс AWG внутри контейнера | `awg0` |
| `--awg-address` | IPv4, назначенный интерфейсу AWG | `10.66.44.1` |
| `--awg-cidr` | Подсеть AWG-клиентов, содержащая указанный адрес | `10.66.44.0/24` |
| `--mt-port` | Порт TCP, на котором telemt слушает на хосте | `5443` |
| `--tunnel-port` | Порт TCP, к которому клиенты подключаются на внутреннем IP AWG | `5443` |
| `--ssh-port` | Действующий порт SSH; используется только для проверки | `22` |
| `--awg-udp-port` | Локальный порт UDP сервера AWG, используемый для исключений | `443` |
| `--bridge-if` | Интерфейс Docker-моста на хосте, необязательный | `br-example` |
| `--bridge-ip` | IP хостовой стороны Docker-моста, необязательный | `172.30.50.1` |
| `--moscow-ips` | Список публичных IPv4 удалённых AWG-узлов для узкого UDP-исключения; имя аргумента сохранено для совместимости | `198.51.100.20,203.0.113.30` |
| `--update-at` | Ежедневное обновление RU-списков, время UTC | `04:25` |
| `--fix-ifupdown` | Разрешить ограниченное исправление конфликта конфигурации `eth0` | Флаг |
| `--no-fix-ifupdown` | Не менять `/etc/network/interfaces` | Флаг |
| `--dry-run` | Проверить предпосылки без изменения системы | Флаг |

Примеры IPv4 из диапазонов `198.51.100.0/24` и `203.0.113.0/24` предназначены только для документации — их нельзя использовать как реальные адреса удалённых узлов.

### Несколько Docker-сетей

При подключении AWG-контейнера к нескольким Docker-сетям автоматический выбор обычно опирается на маршрут по умолчанию контейнера. Если выбор неоднозначен, задайте `--bridge-if` и/или `--bridge-ip` явно:

```bash
sudo bash ./install.sh --dry-run \
  --container amnezia-awg2 \
  --awg-interface awg0 \
  --awg-address 10.66.44.1 \
  --awg-cidr 10.66.44.0/24 \
  --bridge-ip 172.30.50.1 \
  --mt-port 5443 --tunnel-port 5443 \
  --ssh-port 22 --awg-udp-port 443 \
  --no-fix-ifupdown
```

Не задавайте адрес моста по внешнему IP VPS: это **локальный адрес Docker-моста**.

### Исключения для удалённого AWG

Если удалённый AWG-узел использует известный публичный IPv4 и геофильтрация затрагивает требуемый UDP-трафик, можно передать `--moscow-ips`. Исключение ограничено исходным IPv4 контейнера, указанным IPv4 назначения, протоколом UDP и исходным портом `--awg-udp-port`. Оно не открывает публичный TCP-порт MTProxyL.

Если удалённых узлов нет либо исключение не требуется, не указывайте эту опцию. Наличие исключения **не гарантирует** успешного AWG-handshake: сетевые маршруты, параметры peer и внешние ограничения проверяются отдельно.

### Конфликт `ifupdown` и `systemd-networkd`

При одновременной настройке одного интерфейса старым `/etc/network/interfaces` и Netplan/systemd-networkd могут возникать ошибки загрузки сети.

Опция `--fix-ifupdown` разрешает установщику, **только при обнаружении поддерживаемого конфликта**, закомментировать соответствующий фрагмент `eth0` в `/etc/network/interfaces`. Создаётся резервная копия исходного файла. Сетевые службы, интерфейсы и SSH при этом не перезапускаются.

По умолчанию исправление следует оставлять выключенным. Для сложных конфигураций (несколько stanza, объединённые `auto`-строки, нестандартные интерфейсы, VLAN, bonding) сетевую конфигурацию следует исправлять вручную после отдельного аудита.

## Правила безопасности и маршрутизация

### Доступ к MTProxyL

1. В хостовом `INPUT` создаётся собственная цепочка фильтрации, используемая для выбранного TCP-порта.
2. В начале обработки разрешается loopback и строго определённый адрес Docker-контейнера через нужный интерфейс моста.
3. Остальные входящие подключения к этому TCP-порту отклоняются по IPv4; внешний IPv6-доступ также блокируется.
4. Внутри AWG-контейнера DNAT перенаправляет запросы от подсети AWG, адресованные внутреннему IP AWG и порту `--tunnel-port`, к хостовому MTProxyL.
5. Дополнительные правила SNAT/FORWARD обеспечивают обратный маршрут TCP-сессии.

Порт `--mt-port` продолжает слушаться самим MTProxyL на хосте: внешний доступ закрывается **файрволом**, а не изменением bind-адреса приложения.

### Блокировка российских IP-сетей

Для IPv4 и IPv6 создаются отдельные наборы `ipset` на основе:

- IPv4: `https://www.ipdeny.com/ipblocks/data/aggregated/ru-aggregated.zone`
- IPv6: `https://www.ipdeny.com/ipv6/ipaddresses/blocks/ru.zone`

Для `OUTPUT` и `FORWARD` добавляются цепочки, которые возвращают управление для `ESTABLISHED,RELATED` и отклоняют **новые** соединения (`NEW`) при совпадении IP назначения с соответствующим набором.

Это **адресная фильтрация**, а не геолокация в реальном времени. Точность определяется актуальностью и полнотой сторонних CIDR-списков. Фильтрация не означает запрет любого IP с фактическим физическим расположением в России и не заменяет универсальную политику `default deny`.

### Сосуществование с другими правилами

Используются собственные именованные цепочки и пометки `euag3guard`. При штатном применении проект не вызывает глобальные `iptables -F` или `ip6tables -F` и не удаляет правила, принадлежащие Docker, UFW или другим приложениям.

Если другая служба позже перезапишет правила, управляемые службы попробуют восстановить свои цепочки. Совместимость со сложными системами сетевой фильтрации (например, нестандартными nftables-правилами или внешним оркестратором) не гарантируется.

## Автозапуск и обновления

После установки создаются следующие юниты:

| Юнит | Назначение |
|---|---|
| `euag3-port.service` | Ранняя установка ограничений порта и правил исходящей фильтрации |
| `euag3-main.service` | Применение конфигурации после запуска сети и Docker, с ожиданием готовности контейнера |
| `euag3-bridge.service` | Повторная проверка и восстановление правил моста |
| `euag3-bridge.timer` | Периодический вызов bridge-службы; период после завершения около 45 секунд |
| `euag3-update.service` | Загрузка и обновление наборов RU CIDR |
| `euag3-update.timer` | Ежедневный запуск обновления по заданному времени UTC |

Обе основные службы имеют тип `oneshot`; состояние `inactive (dead)` **не всегда означает ошибку**, а `active (exited)` не доказывает прохождение реального клиентского трафика. Для диагностики проверяйте `systemctl status` и журналы.

Команды:

```bash
systemctl is-enabled euag3-port.service euag3-main.service
systemctl is-active euag3-bridge.timer euag3-update.timer
systemctl list-timers --all | grep euag3
journalctl -b -u euag3-main.service --no-pager
journalctl -b -u euag3-bridge.service -n 50 --no-pager
journalctl -b -u euag3-update.service -n 50 --no-pager
```

После первой установки управляемые правила уже применены непосредственно установщиком; основные службы предназначены прежде всего для последующих загрузок.

При обновлении списков используются временные наборы и перестановка `ipset swap`. Если скачивание или проверка списков завершается ошибкой, обновление не должно подменять рабочие списки произвольными данными.

## Проверка работоспособности

### На сервере

```bash
sudo /usr/local/sbin/euag3ctl status
sudo /usr/local/sbin/euag3ctl check
systemctl --failed --no-pager
```

Проверить, что TCP-порт приложения слушается, а защитные цепочки находятся на месте:

```bash
ss -lnt | grep ':5443'
sudo iptables -S INPUT | grep EG3_IN
sudo ip6tables -S INPUT | grep euag3guard
sudo iptables -L EG3_IN -n -v
```

Проверить Docker NAT (имя контейнера заменяется на фактическое):

```bash
docker exec amnezia-awg2 iptables -t nat -L PREROUTING -n -v
docker exec amnezia-awg2 iptables -t nat -L POSTROUTING -n -v
docker exec amnezia-awg2 iptables -L FORWARD -n -v
```

Проверить размеры списков:

```bash
sudo ipset list eg3_ru4 -terse | grep 'Number of entries:'
sudo ipset list eg3_ru6 -terse | grep 'Number of entries:'
```

Наличие правил и записей в `ipset` само по себе не доказывает успешность TCP- или MTProto-подключения.

### С AWG-клиента (Windows PowerShell)

При **включённом** клиенте AWG:

```powershell
Test-NetConnection -ComputerName 10.66.44.1 -Port 5443
```

Ожидаемое значение:

```text
TcpTestSucceeded : True
```

При **отключённом** AWG проверьте публичный IP VPS, например:

```powershell
Test-NetConnection -ComputerName 203.0.113.10 -Port 5443
```

Ожидаемое значение:

```text
TcpTestSucceeded : False
```

`203.0.113.10` — документационный адрес. Замените его фактическим публичным IP сервера, предварительно убедившись, что проверка идёт без VPN/другого маршрута к серверу. Проверка из другого внешнего подключения надёжнее выявляет ошибки ограничений доступа.

> [!NOTE]
> `Test-NetConnection` проверяет только установление TCP-соединения. Корректность секретов, SNI, параметров MTProxyL и настоящего MTProto-сеанса нужно проверять отдельно в совместимом клиенте.

### После перезагрузки

1. Убедитесь, что SSH и внешняя сеть доступны.
2. Проверьте запущенные Docker-контейнеры и внутренние адреса AWG.
3. Проверьте systemd-юниты, таймеры, списки IP и правила проброса.
4. Повторите оба клиентских TCP-теста.
5. Проверьте доступность MTProto через разрешённый путь.

## Управление

Все операции выполняются от `root`.

| Действие | Команда |
|---|---|
| Вывести конфигурацию и состояние | `sudo /usr/local/sbin/euag3ctl status` |
| Проверить зависимости и соединение с локальным MTProxyL | `sudo /usr/local/sbin/euag3ctl check` |
| Повторно применить управляемые правила | `sudo /usr/local/sbin/euag3ctl apply` |
| Применить правила, ожидая готовности контейнера до 180 секунд | `sudo /usr/local/sbin/euag3ctl apply --wait 180` |
| Восстановить раннюю защиту порта и фильтрацию исходящего трафика | `sudo /usr/local/sbin/euag3ctl early` |
| Принудительно обновить RU CIDR | `sudo /usr/local/sbin/euag3ctl update` |
| Удалить управляемые изменения | `sudo /usr/local/sbin/euag3-uninstall` |

Повторное применение правил предназначено для восстановления собственных цепочек и правил, а не для переустановки VPN или редактирования конфигурации приложения.

## Удаление и восстановление

### Полное штатное удаление

```bash
sudo /usr/local/sbin/euag3-uninstall
```

Если основной файл управления недоступен, но исходники сохранены:

```bash
sudo bash ./uninstall.sh
```

Удаление обрабатывает управляемые компоненты: правила хостового файрвола, собственные правила в пространстве AWG-контейнера, созданные `ipset`, службы и таймеры systemd, установленные управляющие скрипты и собственное состояние.

**AWG-контейнер, Docker, MTProxyL, SSH, UFW и Netplan не удаляются.** Если включалось исправление конфликта `/etc/network/interfaces`, исходный файл восстанавливается при условии, что он не был независимо изменён после установки.

### Автоматический откат при ошибке установки

При обычной ошибке установки, `SIGINT`, `SIGTERM` или `SIGHUP` запускается процедура отката. Она использует сведения о состоянии установки и старается удалить собственные изменения, не сбрасывая чужие правила.

**Нельзя гарантировать атомарный откат при любой аварии.** Аварийное выключение питания, `SIGKILL`, недоступный Docker, повреждённая файловая система или сторонние правки могут потребовать повторного удаления или ручного восстановления. При неполном откате состояние и резервные копии сохраняются для анализа и повторной попытки.

При необходимости повторить удаление:

```bash
sudo bash ./uninstall.sh
```

Не следует вручную удалять `/var/lib/euag3guard/`, пока откат не завершился: в нём находятся данные, необходимые для восстановления.

> [!CAUTION]
> После удаления правил ограничения MTProxyL его TCP-порт **может стать доступен из публичной сети**, поскольку сам сервис продолжает работать. Если прокси должен оставаться закрытым, заранее подготовьте отдельное правило ограничения доступа или остановите приложение штатным способом.

## Устранение неполадок

| Симптом | Что проверить |
|---|---|
| `MTProxy TCP ... not listening` | Запущен ли telemt; совпадает ли `--mt-port` с реальным TCP-портом |
| `SSH TCP ... not listening` | Соответствует ли `--ssh-port` действующему порту `sshd`; слушает ли SSH вообще |
| `No IPv4 address on ...` | Имя `--awg-interface` и адрес интерфейса AWG внутри контейнера |
| `AWG ... expected ...` | Параметры `--awg-address` и `--awg-cidr`; они должны совпадать с реальным IP/CIDR |
| `No Docker container interface shares a subnet ...` | Сети контейнера и моста, значение `--bridge-ip`, используемый Docker-интерфейс |
| `Ambiguous Docker bridge selection` | Указать `--bridge-if` и/или `--bridge-ip` |
| `Container net.ipv4.ip_forward must be 1` | Включён ли IP forwarding внутри AWG-контейнера; исправлять средствами настройки AWG |
| `No RU lists available` / ошибка `curl` | HTTPS-доступ к IPdeny, DNS, сертификаты, ограничения исходящей сети |
| Списки `ipset` пусты после загрузки | Журнал `euag3-main.service`, сохранённые CIDR, `euag3ctl apply` |
| Изменилось имя интерфейса Docker | Проверьте `euag3-bridge.timer`, логи `euag3-bridge.service` и повторный `apply` |
| Из AWG TCP-проверка возвращает `False` | Реальный маршрут AWG-клиента, `AllowedIPs`, счётчики DNAT/FORWARD, UFW, telemt |
| Снаружи порт TCP доступен | Порядок правил `INPUT`, IPv6-защиту, сторонние управляющие файрволом службы |
| Откат частичный | Состояние Docker/systemd и содержимое `/var/lib/euag3guard/`; повторить удаление после устранения причины |

Проверка журналов:

```bash
journalctl -b -u euag3-port.service --no-pager
journalctl -b -u euag3-main.service --no-pager
journalctl -b -u euag3-bridge.service -n 100 --no-pager
journalctl -b -u euag3-update.service -n 100 --no-pager
```

Не публикуйте необработанный вывод `euag3ctl status`, `docker inspect`, таблиц маршрутизации, конфигураций VPN и системных журналов: они могут содержать реальные адреса, метаданные узлов или другие внутренние сведения.

## Ограничения

- Это инструмент управления **конкретной схемой** «AWG 3 в Docker → MTProxyL на хосте», а не универсальный VPN-маршрутизатор.
- Не создаёт AWG-peers, не выдаёт клиентские конфигурации, не устанавливает MTProxyL и не конфигурирует удалённый сервер.
- Не выполняет проверку настоящего MTProto-протокола или клиентских секретов.
- Не гарантирует полную классификацию российских адресов по IPdeny и не блокирует автоматически все географически российские серверы вне опубликованных списков.
- Не заменяет отдельные правила безопасности провайдера, настройки SSH, обновления ОС и мониторинг доступности.
- Не гарантирует корректное сосуществование с любыми сторонними правилами `nftables`/`iptables` и автоматическими скриптами очистки цепочек.
- Не гарантирует полное восстановление системы при неконтролируемом выключении питания или параллельном изменении тех же ресурсов сторонними процессами.
- В полномасштабной изолированной среде с новым VPS, Docker и реальными AWG/MTProxyL необходимо отдельно проводить интеграционные проверки после установки и перезагрузки.

## Тестирование

В каталоге `tests/` находятся автономные тесты конфигурации, обработки сетевых правил и отката. Они используют моделирование внешних команд и не заменяют проверки настоящего сетевого пространства Docker.

Для запуска из корня проекта:

```bash
python3 -m unittest discover -s tests -v
python3 -m py_compile euag3ctl.py
bash -n install.sh uninstall.sh
```

Перед использованием в рабочей среде рекомендуется прогнать режим `--dry-run`, затем проверить доступ с реального AWG-клиента и выполнить контрольную перезагрузку.

## Публикация конфигураций и журналов

Для публичного репозитория предназначены исходные файлы проекта и общая документация. **Не включайте**:

- `/var/lib/euag3guard/` и его резервные копии;
- выводы `docker inspect`, `ip route`, журналы systemd и результаты диагностики без удаления адресов и идентификаторов;
- ключи, конфигурации AWG-peers, секреты MTProxyL, SSH-ключи, токены и приватные домены;
- файлы `.env`, личные конфигурационные архивы, дампы файрвола и случайно сохранённые командные истории.

Пример `.gitignore`:

```gitignore
__pycache__/
*.py[cod]
.pytest_cache/
.venv/
.env
.env.*
*.log
*.bak
*.backup
*.zone
*.pem
*.key
*.conf.local
backup/
backups/
state/
```

Публикуемые Git-коммиты и настройки профиля хостинга кода имеют **отдельные метаданные автора**; отсутствие персональных данных в README не удаляет их автоматически. Перед публикацией проверьте историю коммитов, адрес электронной почты в Git и доступность вложенных файлов.
